# Aggregation Table

The dashboard in `plan.md` that lists every effort in the release with its current state. Regenerated by `--update` from the folder contents. Never hand-edited.

## Position

Under `## Aggregation` (between `## Context` and `## Hygiene Gates`).

## Columns (exact)

```markdown
| id | title | spec-status | plan-status | AC-coverage | has-plan? |
|----|-------|-------------|-------------|-------------|-----------|
| S-07 | Retry policy with backoff | committed | executing | complete | yes |
| S-05 | Config loader refactor | draft | (none) | (none) | no |
```

| Column | Source | Notes |
|--------|--------|-------|
| `id` | effort folder name prefix (`<id>_<slug>/`) | |
| `title` | `spec.md` frontmatter `title` | Truncate at 60 chars with ellipsis if longer |
| `spec-status` | `spec.md` frontmatter `status` | `draft`, `committed`, `fulfilled`, `superseded` |
| `plan-status` | `implementation-plan.md` frontmatter `status`, or `(none)` if file absent | `draft`, `committed`, `executing`, `complete`, `superseded` |
| `AC-coverage` | `implementation-plan.md` frontmatter `ac-coverage`, or `(none)` if plan absent | `complete`, `partial`, `unmapped` |
| `has-plan?` | `yes` if `implementation-plan.md` exists in the effort folder; `no` otherwise | |

## How `--update` populates the table

```
for folder in plan_NN_<slug>/<id>_<slug>/:
    spec = read folder/spec.md (skip folder if spec.md missing)
    plan = read folder/implementation-plan.md (None if absent)
    emit row:
        id = effort_id_from_folder_name(folder)
        title = spec.frontmatter.title (truncated)
        spec-status = spec.frontmatter.status
        plan-status = plan.frontmatter.status if plan else "(none)"
        AC-coverage = plan.frontmatter.ac-coverage if plan else "(none)"
        has-plan? = "yes" if plan else "no"
```

Sort by `id` ascending (lexical sort on `S-07`, `S-09`, etc.).

## Edge cases

- **Folder named correctly but no spec.md inside.** Skip with a warning logged in `--update`'s report. Don't emit a row.
- **Folder named `<id>_<slug>/` but `<id>` isn't a real effort id format.** Same: warn, skip.
- **Spec frontmatter missing required fields.** Emit the row with `(invalid)` in any missing column. `--gate` will flag this as a hygiene problem.
- **Effort id appears in `includes:` frontmatter but no matching folder.** `--update` reconciles: removes the id from `includes`. Reports "id S-09 was listed in includes but no folder found; removed from includes."
- **Folder exists but id not in `includes:`.** `--update` reconciles: adds the id to `includes`. Reports the add.

`includes` is regenerated from the folder walk; the frontmatter list and the file system stay in sync after every `--update`.

## What the aggregation table does NOT do

- **Does not show AC fulfillment progress per spec.** That lives in the implementation plan's completion-status table (which the release plan can link to but doesn't reproduce).
- **Does not show file changes or commits.** Use `git log` for that.
- **Does not show owners.** Owner info lives in each implementation plan's completion-status table.
- **Does not link to specs/plans by relative URL.** It assumes the reader is at `plan.md` and can find the effort folder by `id`. (A future enhancement could add a column with a relative link, but v1 keeps the table terse.)

## Why the table is generated, not authored

Hand-authored aggregation drifts:
- Promote/demote happens and the table isn't updated
- Spec status changes and the table still says the old status
- New effort added and forgotten

Generation from disk makes the table always-correct-by-construction. Run `--update` after any promote/demote/spec-status-change to refresh.

## Reading the table for tag readiness

The aggregation tells you what's in scope and where each effort stands. To know if the release is *ready*, look at `--gate`. The aggregation is the inventory; the gate is the verdict.
