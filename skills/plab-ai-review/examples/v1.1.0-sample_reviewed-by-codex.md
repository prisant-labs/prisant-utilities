#### D1: Identity resolution for unauthenticated traffic

**Context:** The plan applies token buckets per "caller identity" but never defines that identity for unauthenticated routes (public `/v1/status`, `/v1/health`, marketing webhooks). Without a defined identity key, two different callers behind the same NAT can starve each other, or a single caller can bypass the limiter by varying a header. This must be resolved before implementation starts.

**Proposed solutions:**

- **Option A:** Raw client IP. Simple, works with existing reverse proxy headers (`X-Forwarded-For`). Pros: one line of code. Cons: shared NAT causes collateral damage; IPv6 rotation defeats it; does not distinguish callers hitting different routes.
- **Option B:** `IP + route-family fingerprint` (e.g., hash of IP + first URL segment). Still simple, but isolates `/status` bucket from `/webhooks` bucket so a noisy health-checker cannot starve webhook delivery. Cons: slightly more state per caller; fingerprint must be stable across deploys.

**Recommendation:** Option B. The extra state is negligible, and per-route-family isolation is the behavior operators will expect the first time they investigate a 429 incident.

---

**Maintainer Response** - 2026-04-22

- **Status:** Accepted
- **Reasoning:** Option B is the right call. Raw IP would conflate `/status` pressure with webhook pressure and generate support noise the first time a customer's office NAT hits a limit.

Also verified with the SRE on-call rotation before accepting - they confirmed per-route-family buckets match how they already triage 429s in the legacy proxy.

#### D2: Redis-backed vs. in-memory token buckets

**Context:** Section 3 of the plan specifies a Redis-backed limiter so all API instances share a single bucket per caller. This adds a hard dependency on Redis availability for every request and meaningfully expands the blast radius of a Redis incident. Pulseboard currently runs single-region with one writer node per service.

**Proposed solutions:**

- **Option A:** Redis-backed shared buckets (as planned). Pros: accurate global counts regardless of instance count. Cons: every request now depends on Redis; doubles the number of systems that can take the API down; adds ~2ms latency per request.
- **Option B:** In-memory per-instance buckets with limits scaled by `N_instances`. Pros: zero new dependencies, no latency impact. Cons: counts are approximate when instances scale; a caller hammering one instance could briefly exceed the intended global rate.

**Recommendation:** Option B for v1. The approximation is acceptable given single-region deployment and current instance counts (3 nodes). Revisit when we add a second region or when instance count exceeds ~10.

---

**Maintainer Response** - 2026-04-22

- **Status:** Rejected
- **Reasoning:** Going with Option A (Redis-backed) despite the over-engineering concern. We already run Redis for session state, so the dependency is not "new" - it is already load-bearing for the API. The 2ms latency is real but acceptable, and I would rather ship accurate counts from day one than rebuild the limiter when we add region #2 next quarter.

#### D3: Shadow-mode rollout phase

**Context:** Section 5 of the plan rolls the limiter out directly in enforcement mode: day 1 it starts returning 429s. There is no period during which the limiter runs silently so we can compare "would-have-blocked" traffic against real customer behavior. If the limits are wrong, the first signal is customer complaints.

**Proposed solutions:**

- **Option A:** 7-day shadow mode - limiter runs, logs decisions, but never blocks. After 7 days review the log, tune limits, then flip to enforce.
- **Option B:** Per-customer opt-in enforcement - pick 3 friendly customers, enforce for them only, expand from there.

**Recommendation:** Option A. Lower-touch, gives a population-level view, and avoids the selection bias of hand-picked customers.

---

**Maintainer Response** - 2026-04-22

- **Status:** Deferred
- **Reasoning:** Directionally agree shadow mode is the right instinct. Holding until I confirm with the observability team whether our existing request-log pipeline can carry the extra "would-have-blocked" metadata without a schema change. If it can, we go with Option A. If it cannot, the shadow phase itself becomes a 2-week project and I need to re-scope.

---

**Maintainer Clarification Request** - 2026-04-22

> If observability says the log pipeline *cannot* carry the extra field without a schema migration, is there a lightweight alternative that gives us most of the signal? E.g., sampling only 429-candidate requests to a separate log, or emitting a single daily aggregate counter instead of per-request decisions?

**Requestor Response - Claude Opus 4.7 (2026-04-22):**

> Yes - two viable fallbacks. (1) *Candidate sampling:* emit a structured log line only when a request would have been blocked, to a new low-volume log stream. This avoids the schema migration entirely because it is a new stream, and at realistic 429 rates (<1% of traffic) the volume is trivial. (2) *Daily aggregate counter:* increment a Prometheus counter `rate_limiter_would_block_total{route_family,identity_bucket}` per decision and review the histogram at end of week. Loses per-request detail but costs nothing to add. Recommendation: do (1) if the new log stream is cheap to create (most pipelines allow this without a migration), fall back to (2) if even that is blocked. Both preserve the core goal of "see the would-have-blocked population before enforcing."

#### D4: Burst-pattern test coverage

**Context:** Section 4 of the plan covers steady-state load tests (100 req/s sustained, 500 req/s sustained) but not bursty patterns. Token bucket algorithms are specifically designed to handle bursts, so not testing bursts means we are not testing the algorithm's main selling point.

**Proposed solutions:**

- **Option A:** Add two burst tests to Section 4's test matrix: (1) 1000 req in 1s then idle, (2) repeating 100-req bursts every 10s. Verifies both bucket-drain and bucket-refill behavior.
- **Option B:** Rely on production traffic shadow-mode data to catch burst issues after the fact.

**Recommendation:** Option A. Burst tests are cheap to write (two additional `k6` scenarios), run in CI, and catch a class of bugs that shadow mode will only surface after a real incident.

---

**Maintainer Response** - 2026-04-22

- **Status:** Accepted
- **Reasoning:** Cheap and obviously correct. Add both scenarios to the `k6` suite.

## Findings

### Problem Definition & Scope

*Whether the plan has correctly identified what rate limiting is meant to solve and for whom - scoping errors here propagate into every other section.*

**Reviewer - Codex (2026-04-22):**

> - **[Minor | High]** Section 1 names three goals (prevent abuse, protect origin, fairness) but does not rank them. Ranking matters because "prevent abuse" optimizes for strict limits and "fairness" optimizes for smooth degradation - these pull in opposite directions when limits are calibrated. → Rank the three goals or explicitly state they are co-equal.
> - **[Note | Medium]** No mention of internal callers (cron workers, admin tooling). Either carve them out explicitly or declare them in-scope; silence will get interpreted inconsistently by the implementer.

**Requestor - Claude Opus 4.7 (2026-04-22):**

> Ranking goals is a fair ask and costs nothing - I will add a one-line priority order in Section 1: (1) protect origin, (2) prevent abuse, (3) fairness. Internal callers: worth explicit scoping. Recommend adding "Internal callers bypass the limiter via a signed header; enforcement is for external traffic only" to Section 2.

### Storage Backend & Dependencies

*Whether the choice of shared storage (Redis) is justified against the cost of adding a hard runtime dependency.*

**Reviewer - Codex (2026-04-22):**

> - **[Major | Medium]** Section 3 commits to Redis-backed buckets without surfacing the trade-off. Every API request now depends on Redis availability, and the plan does not document a degradation mode if Redis is unreachable. Options like "fail open" (skip the limiter) vs "fail closed" (return 503) have very different customer impact and should be an explicit choice, not an implementation detail. → Either specify the Redis-down behavior explicitly, or reconsider whether Redis is needed at all at current scale. See D2.

**Requestor - Claude Opus 4.7 (2026-04-22):**

> Half agree. The degradation-mode question is real and should be answered in the plan regardless of backend choice - flagging separately. On Redis itself: I am recommending Option B (in-memory per-instance) for v1 because Pulseboard is single-region with 3 nodes; the approximation cost is low and the latency + dependency win is meaningful. Raised as D2.
